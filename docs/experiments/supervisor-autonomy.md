# SA1: Opt-in supervisor autonomy experiment

Portable protocol; inactive by default. Each human-approved instance sets its own review cutoff and explicit enrollment register. The owner's dated activation, schedule, thread identities and evidence remain machine-local. This is a temporary overlay for explicitly marked runs, alongside the established workflow.

## Enrollment and treatment

The human must explicitly mark each supervisor run as participating in SA1. Creating this experiment, finding a #SV title, or observing a similar assignment does not enroll it. Record the human message/turn reference and thread identity in that run's existing note and the experiment enrollment register. Do not resume paused runs, start supervision, create/message other chats, or change shared settings through this experiment.

For NEW assignments in an enrolled run, give the worker the approved overall objective, a coherent milestone, relevant evidence, constraints, permitted writes and acceptance criteria. Let it identify obstacles, frame useful questions, investigate credible alternatives and choose the method. Permit a reasoned challenge to the supervisor's framing within scope. Name an expected benefit without prescribing the finding or supplying an implementation recipe. Known corrections may remain precise. All existing authority, independent test ownership, one-writer, final-audit, scope, stop and publication rules remain in force.

The supervisor remains responsible for integration and acceptance. Review at meaningful milestones and consequential decisions; use corrections for observed failures. A diagnostic probe needs a reason tied to the outcome, not a permission ceremony. Research is useful when its result could change a decision; do not invent research to fill a quota.

After a completed session or meaningful milestone, add at most five lines to the existing run note: intended outcome and observed result; worker-originated discovery/decision and what changed because of it; supervisor interventions with reason; failures/rework/drift; evidence references. Missing information stays unknown. Do not add a separate worker reporting system.

The overlay expires for NEW assignments at the cutoff. Preserve in-flight assignments, user stops, acceptance and evidence. No automatic global adoption or reversal. The final evaluation recommends a decision to the human.

## Observation cadence

A daily follow-up in the experiment thread collects all newly completed sessions/milestones since its last cursor, using supported list/read-thread tools and referenced project evidence. The unit of analysis is a meaningful assignment/milestone, with individual completed turns retained as evidence. Merge repeated continuation/check-in turns into the same unit; do not count them as independent successes. Identify records by thread plus milestone and preserve turn IDs to prevent duplicates.

Inspect recent #SV runs and the enrollment register; keep ordinary non-enrolled runs labeled comparison-only. Read-only observation does not enroll them. Prefer comparable work in the same project; report task difficulty, risk, project, model, baseline-policy hash and time-period differences. Saved pre-experiment evidence is descriptive historical context, not a controlled baseline. The collector writes only this experiment's work/records, cursors and outputs. It never directs production work, sends messages, resumes goals, changes monitored notes or adopts workflow revisions.

## Evidence and outcomes

For each record capture:
- identity, enrollment evidence, assignment, milestone type and difficulty/risk;
- actual contract exposure: outcome-owned, prescribed recipe, mixed, or unknown, with a short source pointer;
- user-facing improvement or resolved decision-critical uncertainty, supported by artifacts/checks;
- independent worker problem framing, method choice, findings and challenges, distinguishing these from supervisor-supplied choices and prompted fact extraction;
- consequential worker decisions adopted, supervisor interventions and their reasons, rework/failures, observed scope drift and unresolved limits;
- real reported usage/cost only where supported; unavailable values are null. Calendar elapsed time and turn counts are not active effort or token usage.
- exact evidence references and observer confidence/limits, policy version/hash and changes affecting comparability.

Do not use test/commit/report counts as outcome measures. Do not assume more autonomy is better. Give examples of beneficial supervision and beneficial worker initiative, plus counterexamples. Check the actual assignment against the claimed independent contribution. Treat worker and supervisor success statements as claims to verify.

The primary question is whether outcome-owned assignments produce useful independent decisions AND verified progress without unacceptable drift or rework. Secondary questions concern coordination overhead and which constraints helped. Use an outcome-by-outcome comparison with denominators, missing data and adverse cases. No single combined score or causal claim from this observational opt-in sample.

## Final decision on or after the cutoff

Write a concise decision report: keep, refine, revert this overlay, or insufficient evidence; strongest supporting and contrary examples; what actually improved; problems and their likely causes versus unknown causes; useful new insights; narrow proposed next action and reversible rollback instructions. No global workflow edits, unapproved extensions or automatic reversal.

Fewer than three completed meaningful milestones across two enrolled runs is a low-evidence case study, not a general recommendation. This is a practical minimum, not statistical proof; meeting it does not establish causality. No enrolled runs is a valid insufficient-evidence outcome. Do not silently extend the window.

Finish any final collection, write the report and then pause the observer through the supported automation tool using its saved identity and unchanged fields. If the host was offline at the target time, perform the final review at the first later invocation and disclose the delay.

## Sources and capability limits

The installed automation interface exposes time schedules; a Codex session-completion trigger is not exposed through it. Daily incremental collection is a design choice to reduce monitoring overhead while retaining session-level evidence. Local scheduled work needs the computer on, the app running and its files accessible: https://learn.chatgpt.com/docs/automations?surface=app

Task-specific criteria, recorded evidence, comparisons and human calibration follow OpenAI evaluation guidance: https://developers.openai.com/api/docs/guides/evaluation-best-practices . This experiment does not use or require an external evaluation service.
