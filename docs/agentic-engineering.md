# Learning from long engineering runs

Use this guide when planning, reviewing or learning from substantial agent-led implementation. It is a portable practice guide, not a new approval flow, scheduler or mandatory ceremony for small changes. Project instructions and the user's current scope remain authoritative. The practices below were distilled from a long reusable-media-kit run; their future efficiency benefit has not been established by a controlled comparison.

## Make learning change the next decision

A useful retrospective connects an observed incident to a contributing mechanism, a concrete practice and evidence that would show whether it helped. Preserve what worked as well as what failed. Separate directly observed facts, plausible explanations and untested proposals. Do not manufacture time allocation, productivity gains or general capability conclusions from the length of one run.

Store project facts and acceptance evidence in the project. Promote only general, privacy-safe practices into shared workflow documentation. Link the relevant entry point from project instructions. Do not accumulate a new skill, command, global policy or repeated checklist for every incident; first improve an existing contract or remove ambiguity. Documentation improves continuity but cannot guarantee future compliance. Review the next real outcome.

## Bound the outcome before expanding the implementation

Define a finite acceptance contract: the deliverable, supported behaviors, important state transitions, fidelity limits and release gates. When a user expands the goal, rebaseline that contract and status. Preserve the new scope without silently extending old completion claims or estimates.

Distinguish missing advertised behavior, a product defect, missing evidence and a deliberate approximation. These require different actions. An untested workflow is not necessarily absent; an implemented workflow is not necessarily usable; a plausible approximation is not automatically acceptable. Avoid adding features solely because a reviewer found an opportunity unrelated to the agreed outcome.

Keep one current closure queue. Each open gate needs its scope, owner, next action and evidence. Historical reports remain background. Distinguish implemented, exercised, exported, reviewed and published. Counts and percentages need denominators and uncertainty; unequal rows do not form a trustworthy progress meter.

A finite label inventory does not bound option semantics. For an open contract, state a concrete accepted example, an excluded or qualified boundary and the required editing/output surfaces. Displaying a choice and committing its effects are different obligations. Decide whether a discovery is required by the agreed outcome or is an optional proposal before implementation. Early interaction review helps discover the contract; it cannot guarantee exhaustive prediction.

## Prove a thin complete path, then combinations

Establish one ordinary user path across source, validation, controls, persistence and output before implementing a broad inventory. Do not rely on private activation patches to prove the shipped starting path. Reject invalid operations without partially mutating files, assets, history or recovery state.

Cloning a source model is not a transaction over filesystem effects. Prepare and measure dependencies privately, validate the complete candidate plan, then publish immutable assets and commit source/history. Rejection checks should compare the whole relevant asset inventory and redo state, not only source equality. Preserve old dependencies still referenced by history. Repeated late side effects or duplicated eligibility interpretation are evidence for extracting a shared preparation/commit boundary.

Review interactions early. Identity changes, inherited styling, cloned views, scrolling, layered controls and state restoration often fail at boundaries that individual component checks cannot see. Use a compact stress fixture derived from the actual risks. Test fresh late entry and backward/random state restoration when the product permits seeking or replay. Do not require every Cartesian combination without a reason.

An early minimal output smoke checks the pipeline. Exercise combined stress cases in cheaper preview before polished output production and full acceptance review; the early smoke is not release approval.

Prefer one durable model, explicit capabilities and small shared semantic functions. Keep platform mechanics at appropriate edges. Extract a state planner or shared view rule when it eliminates duplicated interpretation; do not infer that a long task justifies a rewrite. Architecture claims need code and experience evidence.

## Separate independent judgment from scarce execution

Use bounded independent test or review ownership where project policy calls for it. Give workers the behavior contract, allowed writes, relevant source state and clear acceptance boundaries. The lead retains integration, final judgment and scope control. Worker activity is not itself product progress.

Parallelize reasoning and independent reads. Lease scarce browser, emulator, GPU, synthesis or disk-heavy execution when concurrency distorts results. Inspect disk headroom and retained artifact growth before expensive batches. Teardown disposable fixtures on failure. Do not increase timeouts or weaken checks merely to hide contention or a real assertion failure.

Separate observed storage exhaustion from suspected execution contention. An isolated pass under several changed conditions does not identify their individual contributions. Serialization can reduce competing working sets while retained artifact accumulation still exhausts storage; evaluate both remedies against the next real run.

## Stabilize before expensive output

Diagnose the cause of a defect before editing. Exercise the corrected source and ordinary authoring path, then freeze the affected source/output cohort before expensive rendering or release work. Update retained consumers deliberately; do not silently migrate unrelated user work.

Attach acceptance to an immutable identity and a named scope: relevant source/assets/settings, output hash and review conditions. Carry accepted evidence forward when that identity and scope remain valid. A changed filename alias is not a new review. A shared source edit does not automatically invalidate every unchanged prior artifact. Keep rejected evidence rejected and explain what a replacement fixes.

## Use different evidence for different claims

| Claim | Appropriate evidence | Insufficient by itself |
| --- | --- | --- |
| Contract and rejection are correct | Independent source/state/history assertions, fault checks, recovery tests | Assertions mirroring today's implementation |
| Ordinary editing works | Real controls or supported public commands, save/reopen/undo/redo | Directly patched fixture source |
| A visual product looks right | Current references, actual-size stills and motion, independent judgment | Render success or a green geometry suite |
| Time-dependent output restores correctly | Fresh, forward, backward and random observations at meaningful states | Only initial load or forward playback |
| A release is delivered | Current required checks, intended diff, accepted actual artifact and verified publication | Local commits or a feature branch push |

Distinguish product fixes from oracle fixes. Preserve the original failure, state the contract that made the expectation wrong, and retain a meaningful fault-sensitive check. Diagnose rasterization, hidden state and serialization differences instead of automatically accepting or rejecting them. Report full exit statuses; cancellations, resource exhaustion and filtered logs are not passes.

Preserve discovery chronology: a visual review may reveal an obligation missing from green tests; a new assertion protects that obligation; an isolated fault shows the assertion can discriminate. Fault sensitivity does not prove the original oracle was complete. Project records should retain this causal trace, with links to the failure, correction and check, rather than only counts of faults or coverage.

For visual imitation, record reference version and evidence type. A still does not prove motion; documentation does not prove every rendered state; a patent does not establish shipped behavior. Tests support visual judgment and fidelity disclosures, rather than replacing them.

## Finish and evaluate

Make small coherent owned commits for recovery. Complete the actual release contract: current-source verification, independent acceptance where required, final diff review, default-branch publication and remote verification under project protections. Do not let optional expansion consume an unclosed release.

Communicate meaningful changes, findings, uncertainty and next gates. Treat new user messages as steering the active work. Avoid repeatedly answering an old status question or restarting setup from inherited history. Give an estimate only with a clear basis and revise scope honestly when the basis changes.

After delivery, reconcile the retrospective with what actually happened. For the next relevant project, select a few high-value practices, observe whether they were used and record the outcome. Measure what is available—late integration findings, invalidated export reasons, resource failures and unclosed release gates—without inventing precision or creating a monitoring system the user did not request.

## Using these lessons for reusable kits

A kit has several consumers: the shared library, registered starting point, ordinary editor, retained project snapshot and final output. Define which surface owns each contract. Validate normal creation and deliberate snapshot adoption separately. A kit's advertised support should match source validation, visible authoring controls and the output states actually reviewed.

Use [design kits](design-kits.md) for the portable snapshot/provenance model. Each consuming repository should retain its own implementation details, references and acceptance procedure. This guide does not certify any particular kit or replace its current verification.
