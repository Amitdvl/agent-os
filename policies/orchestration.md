# Task Orchestration

- `/goal` is an explicit orchestration trigger. Whenever a user starts a `/goal`, automatically invoke the `orchestration` skill at the beginning of the goal. Treat orchestration as the default path for every `/goal`, including one-feature, one-system, multi-file, and long-running work. Do not silently choose direct execution because the work appears easy or does not obviously need parallelism.
- The orchestration workflow must establish a lead, define scope/non-goals/acceptance checks, and assign bounded worker or reviewer roles when delegation is available. The lead owns integration, verification, the final diff review, and the final Done/Not Done decision. If the runtime genuinely cannot delegate, retain the lead contract and state that limitation explicitly before proceeding. Never claim a model or delegation occurred when it did not.
- For `/goal` work, the user gives standing permission to split one goal across multiple Codex tasks when useful, without asking again, subject to runtime tool restrictions. This is permission, not a requirement: prefer subagents for internal subtasks; create separate user-visible tasks only when the runtime permits that authorization. Keep one parent goal and one accountable lead, assign bounded deliverables, isolate writes, track and integrate every task's evidence, and do not declare completion until the whole goal passes acceptance. Multiple tasks do not mean multiple user-run goal sessions or expanded scope. When drafting a `/goal` prompt, include this authorization explicitly; do not create tasks merely to draft the prompt.
- Outside `/goal`, automatically use the `orchestration` skill when the task has multiple independently valuable workstreams with separate deliverables and evidence, or when a sensitive/irreversible external change needs independent risk review. When the activation decision is genuinely uncertain, ask the human whether to orchestrate.
- Delegate bounded assignments with allowed files/systems, constraints, verification, and required evidence. Do not allow concurrent edits to shared mutable surfaces; sequence work or isolate it in worktrees.
- Prefer a stronger planning/review model for the lead and an execution model for workers only when the runtime exposes and accepts model selection. Otherwise use available agents with the same lead/worker separation. Never claim a model or delegation occurred when it did not.
- The lead independently reviews worker output, runs final verification, inspects the final diff, and reports residual risks.
