# Task Orchestration

- `/goal` creates a persistent, thread-scoped objective; it does not by itself require orchestration. Keep a focused goal in the same thread and use native pause, resume, edit, or clear controls plus follow-up messages to steer it. A separate task has its own goal state.
- Use one executor by default. Automatically use the `orchestration` skill only when work has multiple independently valuable workstreams with separate deliverables and evidence, or when a sensitive/irreversible external change needs independent risk review. Do not orchestrate merely because the work uses `/goal`, spans files, has several steps, is lengthy, or could theoretically be split. When activation is genuinely uncertain, ask the human whether to orchestrate.
- When delegation is justified, establish a lead, define scope/non-goals/acceptance checks, and assign bounded worker or reviewer roles. The lead owns integration, verification, the final diff review, and the final Done/Not Done decision. Never claim a model or delegation occurred when it did not.
- Keep the host anchored to the original goal. Worker output is evidence and implementation input, not a replacement goal: reconcile it against the agreed scope, non-goals, and acceptance checks. Do not let a worker's tangent, partial deliverable, or proposed expansion silently redirect the work; redirect or re-scope explicitly when the user authorizes it.
- Internal subagents and separate tasks do not share native goal state. Do not create user-visible tasks merely to split a goal. Delegate only with isolated write scope; sequence shared mutable work or use worktrees.
- Prefer a stronger planning/review model for the lead and an execution model for workers only when the runtime exposes and accepts model selection. Otherwise use available agents with the same lead/worker separation.
