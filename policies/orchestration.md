# Task Orchestration

- `/goal` creates a persistent, thread-scoped objective; it does not by itself require orchestration. Its text is both the first prompt and the completion criterion. Keep related work in the same thread and use native pause, resume, edit, or clear controls plus follow-up messages to steer it. A separate task has its own goal state.
- Substantial Codex projects, including multi-session or multi-track work, must operate inside a matching Codex project rather than remain only in Recent chats. At the start, on resumption, or when a small task grows into substantial work, identify and reuse the matching project; create one through supported app tools or UI when none exists. Check existing projects first and avoid duplicates. A sidebar section is not a Codex project.
- Codex owns project organization: automatically move the active main or supervisor chat and related worker chats into that project, and place future related chats there at creation. Do this without asking the user to perform the move or requesting routine confirmation. Move only chats belonging to the work; preserve their IDs, history, goals, execution host, and checkout/worktree ownership. Verify actual project membership through supported app state before reporting success.
- Use only supported installed capabilities for project creation and chat moves, honor permissions and deliberate human stops, and never edit app internal state to simulate membership. If creation or movement is unavailable, record the exact blocker, complete available in-scope work, and leave project organization explicitly unfinished; do not claim that chats moved.
- Apply the core **Implementation test ownership** checkpoint before choosing one executor for substantive implementation. Eligible testing gets one bounded `cover-project` worker even when production work is sequential; routine tasks and explicit constraints stay direct. This testing assignment needs no larger team.
- Run independently actionable implementation, testing and review tracks in parallel unless a concrete reason makes that ineffective or unsafe. Use `orchestration` for multiple valuable workstreams or consequential independent risk review. Parallel feature writers use isolated worktrees or disjoint mutable surfaces, with one lead integrating and verifying. Never impose one production writer for the whole project unless explicitly requested or required by an actual dependency, atomic shared-state operation, unavailable capability or concrete coordination/resource cost. State the reason and affected scope; serialize conflicts, not the project, and revisit the exception when the constraint changes. Do not create filler tasks or layers merely to fill agent slots. Respect actual concurrency, model and worker-type restrictions.
- Increase throughput when independent work can finish faster and more efficiently in parallel. Keep available agent slots productively assigned to bounded, non-overlapping work; replenish finished lanes promptly, and stagger expensive shared tests or native work when contention would slow the whole task. Report the actual active-agent count and runtime limit rather than implying concurrency that is unavailable.
- Never create or launch more than eight Codex App chats at the same time. Eight is the app-wide ceiling: count existing active chats along with chats for the current task, including supervisor, worker, auditor, and page chats. Check the current count before creating a chat; if the count is unknown or already eight, reuse an existing chat or wait until a slot is free. Internal subagents that do not create app chats do not consume a chat slot.
- For a broad outcome the user explicitly wants accelerated, derive top-level acceptance workstreams from the remaining goal, assign bounded outcome contracts, and let workers reason from first principles within their ownership and evidence limits. Aim to sustain about ten confirmed active, independently useful lanes when work, tools, and host resources permit. Reconcile the lane roster with compact, batched status checks at worker handoffs, blockers, and integration checkpoints. Replenish useful lanes when those checks show available capacity. Read full worker histories only when needed to review a handoff or diagnose a failure. Use local agents, Codex pages, and isolated CLI sessions as needed. Scale back only for observed contention, conflicting ownership, or exhausted useful work, and report the reason.
- Give production workers high-level domain or player-journey outcomes that persist through their dependent steps: evidence recovery, implementation, connected operation, focused verification, correction, and the next source-ready family. Let each worker plan the order from first principles inside exclusive ownership. A single test, note, or one-off fix is a checkpoint, not the whole assignment, unless it proves a real blocker or completes the outcome. Hand coherent verified batches to the lead promptly while the worker continues useful work; assign independent reviewers to challenge the integrated result.
- When delegated work requires another owner to integrate, review, verify, unblock, or continue it, deliver a direct handoff before calling that work complete. Name the exact branch, commit or artifact, checks and evidence, remaining gaps, and the action needed from the receiver; verify delivery through the supported coordination channel. Do not notify the lead for self-contained work or information already delivered that needs no lead action, and do not send duplicate status messages. If the necessary handoff cannot be sent under the tool's authority or access rules, report the undelivered handoff as a blocker.
- For an explicit short deadline, create a supported task clock or heartbeat with a known stop time, inspect actual progress at meaningful checkpoints, and redirect capacity to the critical path. Plan dependency order and non-overlapping write scopes before scaling a wave; measure accepted integrated behavior and verification, not launch count. A clock does not waive source provenance or final acceptance.
- At each integration handoff and before assigning new work, reconcile the active backlog with current commits, evidence, and test results. Close completed rows, update stale blockers, merge duplicates, and reprioritize source-ready work. Preserve unresolved historical gaps and provenance.
- When the user explicitly asks for more parallel capacity than the current agent runtime allows, use separate Codex pages to run additional bounded, independent workstreams when that capability is available. Give each page an isolated checkout and explicit file ownership, replenish pages after their assignments finish while useful work remains, coordinate integration centrally, and report the number actually running rather than counting idle pages as capacity or completion.
- Treat every task and goal as a five-hour delivery target from its latest human start or reset, regardless of size. Immediately decompose independent outcome work, use the available parallel capacity aggressively, and keep useful lanes replenished; do not spend long stretches serially debugging while independent work waits. Recheck the critical path and accepted output at meaningful checkpoints. If the target is at risk, add bounded lanes or change the approach around the observed bottleneck. Preserve the actual acceptance criteria and report any remaining gap truthfully at the five-hour mark; a deadline never turns partial evidence into completion.
- If Codex App page creation is stalled or unavailable, use the installed Codex CLI to run bounded independent sessions in isolated Git worktrees when that increases useful throughput. Keep assignments non-overlapping, integrate centrally, and report CLI sessions separately from visible app pages, counting only sessions confirmed running.
- A local collaboration runtime's agent-slot limit applies only to that interface, not to the project's total parallel capacity. Do not impose an arbitrary fixed cap on independent Codex pages or CLI sessions; add bounded, isolated lanes while they improve net throughput, and scale back for measured resource contention, conflicting ownership, or verification cost. Count and report only sessions confirmed running.
- Continuously identify the highest-leverage current blocker. Dispatch bounded evidence-recovery lanes when source is missing and bounded implementation or fix lanes when evidence is ready; promptly replenish, stop, or reprioritize lanes according to accepted progress. Preserve independent verification and avoid contention or shared-file conflicts.
- When delegation is justified, establish a lead, define scope/non-goals/acceptance checks, and assign bounded worker or reviewer roles. The lead owns integration, verification, the final diff review, and the final Done/Not Done decision. Never claim a model or delegation occurred when it did not.
- Keep the host anchored to the original goal. Worker output is evidence and implementation input, not a replacement goal: reconcile it against the agreed scope, non-goals, and acceptance checks. Do not let a worker's tangent, partial deliverable, or proposed expansion silently redirect the work; redirect or re-scope explicitly when the user authorizes it.
- For long-running work, keep the active milestone and next action tied to observable outcome improvement or resolution of a critical uncertainty in existing task notes when available. Supporting research, harness and review work needs a named dependency and exit condition; counts and acknowledgments alone are not progress. Diagnose repeated nonprogress from current evidence, allow a no-drift verdict and verify corrections through subsequent actions. Preserve required checks and honest unknowns; status questions do not change scope or resume paused work. Use the detailed `goal-supervisor` contract only for an approved supervised run; this rule creates no new orchestration, logging framework or budget.
- Internal subagents and separate tasks do not share native goal state. Use separate chats for a concrete capacity or lifecycle benefit when the human has authorized them; do not let chat creation replace accepted output. Delegate only with isolated write scope; sequence shared mutable work or use worktrees.
- Select each assignment's model and reasoning effort deliberately when the runtime supports it. Do not dispatch new work to GPT-5.6 models. Use an appropriate GPT-6 family model: GPT-6 Sol Medium for ordinary implementation, focused tests, catalog processing and bounded investigation; GPT-6.1 Sol High for difficult reasoning, architecture or subtle security and persistence decisions. Medium is the routine supervisor default where supported; reserve High for consequential decisions and difficult review, while keeping independent final acceptance. Respect actual model availability and human preferences. Never select Ultra or substitute an arbitrary weaker model when risk calls for stronger reasoning. Escalate demonstrated reasoning difficulty, not missing assets, permissions, resource limits or tool failures. Prefer fresh worker context with a compact contract, relevant files and acceptance checks; pass full history only when needed. Use scripts or shared pipelines for repetitive catalog work. Measure accepted results, usage, elapsed time and rework on representative batches before claiming savings. Do not add a monitoring project or unrequested hard budgets. Never claim a model or reasoning setting the runtime did not accept.

- When the human defines a high-level objective suited to repeated discovery and review, proactively recommend `goal-supervisor` through the native human question box. Keep the run off until the actual human reply explicitly approves supervision with subagent delegation and creating/messaging separate worker chats when useful for that objective; ordinary task approval, preselection, silence and question-delivery acknowledgment do not count. Honor any human restriction on worker type. If the question tool is unavailable, disclose that and ask in ordinary text without starting. Do not repeat a declined offer without a material scope change or human request.
- An approved `goal-supervisor` run keeps a persistent native supervisor goal and defaults to internal subagents for bounded passes. Use a separate worker chat only when its own native goal/independent continuation, direct human steering/revisiting, another project/host or another concrete lifecycle/configuration benefit earns it, or as a supported fallback when subagents are unavailable; record the reason. Subagents do not need their own native goals; separate chat workers manage their own. Use parallel feature writers with isolated ownership and one integration lead; keep one writer per shared mutable surface in a checkout and sequence only conflicts. Prefix the supervisor chat title with `#SV ` at start or resumption, preserve exactly one prefix on later renames and after completion, and leave worker/auditor titles unmarked. Use a short outcome brief in the start proposal, choose each pass from the current obstacle and expected improvement, review with evidence suited to the discipline, verify the whole main journey, and require a fresh independent final auditor to accept the current result after corrections/re-audit before completing the supervisor goal. Do not configure cycle, time or token budgets unless requested. Preserve deliberate pauses, reconcile uncertain agent/chat launches before retrying or replacing workers, and propagate human stops through the actor's supported controls; pausing the supervisor alone does not establish that workers stopped. Follow the skill's recovery and stopping contract. This opt-in workflow is distinct from automatically delegating an ordinary goal.
- Supervisor authority boundary: ask the human and wait for explicit approval of the concrete target/action before system-wide or user-global installs/updates/removals of shared toolchains, SDKs, drivers, runtimes, packages or services, machine-configuration changes (including remote hosts), or major scope expansions beyond the approved outcome. Broad run approval, agent-drafted goals, supervisor technical review, worker recommendations and OS/UAC prompts do not grant this authority. Check before dispatch and execution; pass actual human approval references to workers, which must stop the gated branch if missing. Prepare a concrete proposal with impact and alternatives; continue independent in-scope project-local work while awaiting a reply. Already explicit human authority need not be requested again unless the action materially changes; human rejection or deliberate human cancellation does not authorize another route. Ordinary project-local edits, isolated dependencies, tests, builds and reversible in-scope choices remain autonomous; inspect actual command effects. This boundary overrides general local-work autonomy and must be checked in the final audit, which cannot retroactively authorize changes.
